# DeepSeek 输出消耗修复

状态：用户已将目标调整为两个对话协作的“省钱与翻译质量”。本方案保持为未启用实验，适配器已隔离到 output；不再单独推进。实际分工及证据以 `docs/2026-10-17-cost-quality-collaboration.md` 为准。

用户要求修复翻译软件的输出 token 过多，并以翻译质量为优先。已有 189 次真实请求：输入 232,534，输出 501,104，其中思考 445,273（88.86%）。术语提取占输出 298,178、思考 272,181。截图本身不能拆分思考比例，以上数据来自已有实验记录。

采用同页术语批次合并，而不降低所选的 low/high/max、关闭思考、限制生产输出预算、删减术语规则或跳过正文。上游在同页约 600 token / 13 段后提交任务；适配器收集这些既有批次，合并相邻批次到不超过 1,800 源文 token / 36 段。跨页不合并，超限的既有批次原样保留。过滤、源文顺序、术语提示词、用户词表、输出解析、进度计数继续使用上游实现。新适配器只在官方 DeepSeek 的翻译进程启用，不修改供应商目录，也不涉及缓存优化模块。

单元测试验证源文和顺序完整、每段仅出现一次、边界与跨页隔离、原有过滤和进度不变、重复安装安全；真实引擎对本地 HTTP 模拟服务验证实际请求合并。真实 API 对照只保存最终术语及 usage，不保存密钥或思考正文；保持 High 并检查术语覆盖。只有实测支持节省、且没有发现术语损失，才默认启用。此检查不能构成对任意论文质量不变或固定节省比例的保证。

已完成的 PDF 继续复用；请求的源文与术语上下文发生变化时，现有缓存键自然隔离。安装包必须包含适配器源文件，Windows spawn 子进程也安装该适配器。
