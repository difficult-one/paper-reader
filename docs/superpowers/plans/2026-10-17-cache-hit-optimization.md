# 缓存命中率优化总方案与实施计划

> 执行状态更新：用户已明确要求照此方案修复。五个代码阶段及离线回归已实施，真实 DeepSeek 对照仍待用户确定论文范围和费用上限。原始方案保存在修改前源码备份中；实施记录见 `2026-10-17-cache-hit-validation.md`。

**Goal:** 提高真正可复用输入的服务端缓存命中率，减少相同翻译的重复请求，用真实命中/未命中 token 与请求数量验证节省。

**Architecture:** 沿用现有 Electron 主进程翻译网关和 BabelDOC。先增加请求级计量及前缀诊断，再稳定请求前缀并验证冷启动调度，最后增加段落级本地复用及翻译/排版缓存分离。固定论文/章节前缀作为独立对照方案评估，不直接引入不断增长的历史。

**Tech Stack:** TypeScript、Node.js HTTP/文件存储、Vitest、现有 Electron 与 BabelDOC 集成测试。

**状态与日期:** 2026-10-17，0.1.8 已实施、打包并通过离线及打包版验证。真实付费对照待用户确定范围和预算。

## 1. 范围和约束

- 本次只优化缓存链路及必要的计量，阅读、排版、批注、安装方式和其他功能保持现状。
- 服务地址、所选模型、思考开关与档位、输出预算、科研翻译规则保持现状。
- 请求中的有效正文、术语、标题、公式和样式信息完整保留；新术语及时参与翻译。
- 本地复用与服务端命中分别统计。本地复用不冒充服务商缓存命中。
- 未返回的 usage 字段标记为缺失；推算值单独标记，不伪装成服务商原始值。
- 不通过填充重复文字或无用历史提高百分比，不加入额外收费的虚拟预热请求。
- 不移植 Reasonix 仅针对其他服务路由的请求头作为 DeepSeek 官方缓存开关。
- 翻译规则、模型、思考档位或有效上下文不同的缓存不能混用；旧译文不自动覆盖。

## 3. Reasonix 与 DeepSeek Harness 的参考结论

**DeepSeek Harness:** 会话中的既有消息保持原样，后续内容追加到末尾；修改或替换早期内容会破坏相应位置之后的复用。这解释了长会话中旧上下文占比很高时，命中率可以很高。[会话实现说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/session/README.md#model-experience)

**Reasonix:** 不只显示命中率，还保存系统提示、工具与会话上下文的指纹、前缀变化原因，以及服务商返回的命中和未命中 token。其测试检查历史前缀是否原样保留，并校验统计分母。本项目优先借鉴确定性组装、变化诊断和真实计量，不照搬编码智能体的全部历史。

- [缓存指纹与变化诊断](https://github.com/esengine/DeepSeek-Reasonix/blob/main-v2/internal/agent/cache_shape.go)
- [前缀保持及统计测试](https://github.com/esengine/DeepSeek-Reasonix/blob/main-v2/internal/agent/cachehit_e2e_test.go)
- 本次源码检查基于 Reasonix `main-v2` 的提交 `99c1626d0140d354a2d50065f007e72f6d61a7a2`，便于后续追溯。

**DeepSeek 官方规则:** 缓存前缀必须先持久化；请求边界、公共前缀识别和长输入/输出的固定间隔可形成缓存单元。公共前缀相同不代表首次并发请求立即命中。缓存建立需要数秒，服务采取尽力而为策略，不保证 100%。[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)

论文独立批次的新正文比例与智能体长历史不同，不能直接把 Reasonix/Harness 的某个百分比写成本软件的保证指标。

## 4. 总体处理流程

```text
翻译任务
  → 读取有效的完整译文缓存
  → 识别请求类型，组装确定性的模型输入
  → 读取完整请求缓存 / 段落缓存并合并相同在途请求
  → 对仍需远端处理的内容应用前缀分组与冷启动调度
  → 向现有服务发送真实翻译请求
  → 记录原始 usage、前缀指纹、耗时和重试情况
  → 校验输出结构与占位符，保存有效结果
  → 生成原有中文 PDF
```

完整译文或本地请求缓存已经命中时，不为了收集服务端命中率额外调用 API。

## 5. 第一阶段：请求级计量与缓存诊断

先保持请求内容和发送行为不变，建立可以比较的基线。

### 5.1 每次请求记录什么

| 分类 | 字段与口径 |
| --- | --- |
| 请求定位 | 任务 ID、请求 ID、请求类型、逻辑请求指纹、尝试序号、时间 |
| 服务与模型 | 服务标识、请求模型、响应实际模型（如返回）、思考档位 |
| 原始用量 | `prompt_tokens`、`prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`completion_tokens`、思考 token；保留缺失状态 |
| 前缀诊断 | 模板版本、规则指纹、固定论文上下文指纹、术语指纹、固定前缀指纹及长度、相邻同组请求的首个变化位置 |
| 请求状态 | 在途数量、耗时、HTTP 状态、完成/错误/取消、是否复用本地结果、是否等待相同在途请求 |
| 数据完整性 | usage 来源、是否可计算比例、是否含推算、计量字段是否一致 |

请求类型区分术语提取、批量正文、单段回退和未知模板。不同模板分组比较，避免把正常的模板差异误报为前缀被破坏。

诊断日志只保存统计、类别、长度和不可逆指纹，不保存密钥、正文、完整提示词或回复。现有翻译缓存的内容存储规则不因此改变。日志在本机按任务保存并轮转，写入异常不导致翻译失败；记录缺失会体现在报告完整性中。

### 5.2 统计规则

```text
单次服务端命中率 = H / (H + M)
任务服务端命中率 = ΣH / (ΣH + ΣM)
```

H、M 使用同一批可计算样本。不能平均每次请求的百分比，不能将本地命中计入 H，也不能把缺少命中字段的请求当作 0% 或 100%。报告附上可计算样本数 / 远端请求总数。

当服务未返回 M，但明确返回输入总数 P 和 H，且 `0 ≤ H ≤ P` 时，可另外计算 `M = P - H`，并标记为推算。服务直接返回的 H、M、P 矛盾时标记异常，不悄悄修正原值。

一次逻辑请求的每次远端尝试分别记录；没有 usage 的超时或错误保留“用量未知”，不能宣称该次费用为零。输出总量如已包含思考 token，不再次把思考 token 加入输出计费量。

### 5.3 如何解释未命中

- 首次观察到该前缀：标记本地观察到的冷启动，不断言服务端一定没有缓存。
- 规则、术语、上下文或协议形状变化：列出客户端实际变化及发生位置。
- 公共前缀稳定、正文不同：明确新正文自然无法复用，不把它算成实现错误。
- 客户端可复用前缀稳定但仍未命中：记录现象；没有服务端证据时，不把原因直接写成缓存过期或服务故障。
- usage 缺失：报告计量不足，不能据此判断真实命中率。

**本阶段交付:** 本机请求日志、按请求类型分组的任务汇总及一份基线报告。缓存统计区域只补充必要的 miss/数据完整性信息，不扩展成新的界面项目。

## 6. 第二阶段：稳定所有可复用前缀

以诊断中实际出现的提前变化为修改依据。

1. 固定系统规则和输出协议；同一模板、同一规则版本的固定文本保持完全一致。
2. 使用稳定的对象键序、编码和空白格式；不为了排序而改变正文数组顺序或原文字符串。
3. 稳定内容靠前：通用规则 → 已确定且不变的论文上下文 → 当前请求需要的术语/章节信息 → 当前批次正文。
4. 任务开始时已有的固定术语形成不可变快照；后续新增或变化的有效术语完整放在变量区。不能冻结旧表并忽略新术语，也不额外提取整篇术语来制造缓存前缀。
5. 批量、术语、单段回退分别保持自己的稳定模板；未知模板只计量，不擅自重写。
6. 时间、请求 ID、临时目录及调度信息只进入诊断，不加入模型可见的稳定区。

**本阶段验收:** 只替换当前批次正文或临时批次 ID 时，固定区指纹不变；真正影响翻译的规则/术语变化能够被识别。所有原有效内容、JSON 合同和公式占位符保留。实际服务端收益另用真实 usage 验证。

## 7. 第三阶段：按公共前缀控制冷启动发送

目前多个冷请求可能在公共前缀写入服务端缓存前同时发出。这是需要对照验证的假设，不预先宣称已确认。

- 按服务、模型、思考档位、模板和实际公共前缀分组。
- 本地查缓存和相同请求合并先执行，调度器只管理必须发往远端的请求。
- 每组冷启动最多约束前两个不同的真实远端请求，初期限制同时在途数量；已有可用命中证据时提前恢复原有并发。
- 复用完成后的正常任务继续建立公共前缀；不添加空请求、虚拟长请求或专门收费的预热调用。
- 不假定第二个或第三个请求必然命中，不无限等待服务端缓存。若固定区很短、请求很少或对照未见收益，该组沿用原发送方式。
- 只改变发送时序，任务内的 QPS、最大并发上限、重试上限与错误语义保持现状。取消、失败、429 及退出必须释放调度等待。

**本阶段验收:** 没有额外逻辑请求；冷热状态隔离正确；取消不挂起；在足够请求数的相同负载下，报告冷启动耗时及未命中 token 的变化。若没有可重复收益，不默认启用这项时序调整。

## 8. 第四阶段：段落级本地复用

让已经有有效译文的段落不因临时批次划分改变而重复付费。

### 8.1 复用边界

键包含服务、模型、思考档位、语言方向、翻译规则版本、原文、公式/样式占位符和有效上下文指纹。有效上下文覆盖论文身份、标题、章节、术语及原请求中可能影响该段含义的上下文。

临时段落 ID 和批次 ID 只用于返回映射，可以排除出内容键；不同学科、不同术语或不同上下文不能仅因句子相同而复用。初版不做模糊语义匹配，也不把不同占位符映射强行合并。重组批次只有在有效上下文仍相同时才复用，不能无条件承诺所有重组都命中。

### 8.2 部分命中与失败处理

- 批次全部命中：本地重建原要求的 JSON，不发送远端请求。
- 部分命中：仅请求未命中的段落，维护原 ID 与远端 ID 的映射，按原顺序合并。
- 相同段落同时出现在不同请求：在上下文相同的前提下共享在途结果。
- 分别校验段落 ID、非空输出、公式与样式占位符；缺段、截断或异常响应不成为成功缓存。
- 有效段落独立落盘，任务取消或网络失败后保留已确认的结果。
- 远端错误保留原错误语义；不能为凑完整结果返回缺段 JSON。

本地复用次数独立显示，远端命中比例只统计真实远端请求。新增段落缓存采用独立命名空间，已有请求缓存保持兼容的只读回退；不把不兼容的旧策略结果算作新策略命中。

**本阶段验收:** 相同原文和上下文再次处理时，已缓存段落无新增远端请求；部分命中只发送剩余段落；模型、规则、术语和上下文改变均正确失效。

## 9. 第五阶段：分离翻译缓存与 PDF 排版缓存

将当前统一版本拆为翻译策略版本和布局/排版版本。

- 完整 PDF 缓存仍考虑源文件、翻译策略和排版版本。
- 段落译文缓存只因实际影响翻译的内容、规则、模型和上下文变化而失效，不因窗口样式或纯排版版本变化而整体失效。
- 修排版后可重新运行解析/排版，在需要译文时由本地缓存提供。未改变且上下文一致的段落不重新请求 API。
- 重新解析导致分段、占位符或上下文改变的部分，按新键处理；不为了零请求错误拼接旧译文。

**本阶段验收:** 仅改变排版版本时，可复用译文仍然命中；源文和翻译策略改变时不会误用。旧 PDF 和已有批注保持各自版本关联。

## 10. 更接近 Harness 的备选：固定论文或章节前缀

如果默认方案仍受限于每批新正文占比，可单独评估：先建立固定的论文/章节原文前缀，后续请求只在末尾指定当前要翻译的段落及输出合同。所有请求共用同一原文前缀，不携带无关论文或不断增长的历史译文。

这个方案可能使更多输入成为可命中前缀，但会增加每次重复发送的缓存输入量和冷启动开销。因此必须和“稳定前缀的独立批次”比较整个任务的 H、M、输出量与费用，不能只比较百分比。

推荐顺序：先做上述五个阶段。备选方案先离线测算输入规模；只有明确具备成本优势的样本，才安排受预算限制的真实对照。整体费用、完整性或术语一致性未通过时不启用。该备选不是把整段历史直接加到现有所有请求中。

## 12. 验收与对照口径

### 12.1 可确定验收的行为

| 场景 | 必须达到的结果 |
| --- | --- |
| 有效完整译文缓存、相同设置再次打开 | 无新增远端翻译请求 |
| 已有段落结果，相同原文和有效上下文再次翻译 | 对这些段落无新增远端请求 |
| 一个批次只有部分段落未命中 | 仅请求缺少的段落，返回数量、ID 与顺序完整 |
| 只改变临时请求/段落 ID | 不破坏内容相同且上下文一致的复用 |
| 模型、档位、规则、术语或有效上下文变化 | 正确失效，不混用旧译文 |
| 服务缺少缓存 usage | 明确缺失，不制造 0%/100% 或虚假节省 |
| 失败/取消/损坏响应 | 不写入伪成功缓存，保留已确认的有效结果 |

### 12.2 服务端效果如何比较

使用同一论文或明确相同的片段、服务、模型、档位和翻译规则，分别报告：

- 真实远端尝试数、成功/失败/usage 缺失数量。
- 累计 H、M、输入、输出及思考 token；同时报告分母覆盖率。
- 整个任务的命中率，和去除本地观察到的冷启动阶段后各类型的比例。
- 有效公共前缀占输入的比例、客户端前缀变化次数及原因。
- 本地复用的请求/段落数量，以及重复任务新增的远端请求数。
- 总耗时和冷启动阶段增加的等待。
- 按服务商当时适用价格折算的任务费用；记录价格来源与时间，思考量不重复计价。

A/B 顺序会影响同一账号的服务端缓存。离线可固定请求序列和模拟服务状态；真实服务没有可依赖的客户端“清空缓存”开关，因此需交替顺序、记录每次冷/热状态并重复验证。不能把 A 先付费建好缓存后 B 的热命中，直接全算成 B 的实现收益。

本轮不运行真实付费测试；实施阶段的真实对照先明确论文范围和费用上限。输出或耗时明显波动时保留记录，不选取最高命中率的一次作为结论。

### 12.3 目标的边界

目标是可复用前缀更充分地命中、同样内容不重复请求，并证明费用减少。新论文首次翻译必然包含此前没有处理的新信息，不把固定的 95% 或 100% 写成无条件保证。若命中率提高但任务费用未下降，相关策略不作为默认改进交付。

## 13. 交付物

1. 仅涉及缓存链路与必要计量的代码改动。
2. 服务商原始 H/M 与前缀变化诊断日志，以及可计算样本覆盖率。
3. 完整请求缓存、段落缓存和 PDF 缓存各自的命中/失效说明。
4. 同条件对照报告，区分离线/模拟验证与真实服务测量。
5. 回归通过后的安装包，以及保留旧数据的升级/回退说明。

**推荐实施顺序:** 计量诊断 → 稳定前缀 → 有界冷启动调度 → 段落复用 → 翻译/排版缓存分离。固定论文/章节前缀保留为有成本依据的对照选项。
