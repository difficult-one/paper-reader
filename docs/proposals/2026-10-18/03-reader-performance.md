# 总体流畅度与连续滚动优化方案

日期：2026-10-18。推荐：**在现有 PDF.js 阅读架构上建立覆盖画布、文本层和后台工作的统一调度与资源预算，并把真实连续滚动的帧耗时纳入发布门槛。**

“彻底杜绝”应转化为可验证的设备与文档范围：在明确支持范围内消除可复现卡顿。不能对任意损坏 PDF、任意显卡驱动和内存压力作永不卡顿承诺。本方案不会以降低滚轮响应、丢弃输入或长期空白页面冒充流畅。

## 1. 当前实现与证据

本次进行静态代码检查和既有结果复查，没有重新运行性能录制。下列“已存在”是源码事实，“待验证风险”需在用户问题文件上通过 trace 证明。

### 已存在的优化

- 页面几何位置缓存及二分定位，滚动不逐帧遍历全部页面读位置。
- passive scroll + requestAnimationFrame 合并，同步阅读位置与全局状态分开。
- PDF 页面组件 memo、IntersectionObserver 按需渲染、离开范围取消绘制。
- 单画布约 800 万像素上限；双栏共享 `pdf-render-scheduler.ts` continuation 队列。

不能简单建议“加防抖、加懒加载、加 memo”作为完整解决方案，这些措施已部分实施。

### 既有测试结果

| 文件 | 负载 | P95 帧间隔 | 超 50 ms 帧数 | 其他 |
| --- | --- | ---: | ---: | --- |
| `output/playwright/scroll-before.json` | 96 页双栏，200 帧 | 23.6 ms | 2 | 页面几何读取 114,624 次 |
| `output/playwright/scroll-after.json` | 96 页双栏，200 帧 | 16.7 ms | 0 | 页面几何读取 0 次 |
| `output/playwright/wheel-scroll-after.json` | 300 次滚轮，1,216 帧 | 20 ms | 1 | 每帧最多绘制 1 个画布，记录的 longTasks 为空 |

两种负载不可直接比较成统一提升比例。Long Tasks API 没有记录长任务，也不代表没有丢帧：布局、合成、GPU 或不足 50 ms 的连续主线程工作都可能影响帧间隔。

`scripts/scroll-smoke.mjs` 目前主要断言滚轮到达、实际发生新页绘制、每帧最多一个画布、几何读取和像素上限；**虽然记录 P95/长任务，尚未把帧耗时和长任务数纳入失败条件**。

## 2. 代码中需要优先验证的风险

| 位置 | 已观察到的行为 | 可能造成的问题，需录制验证 |
| --- | --- | --- |
| `PdfPane.tsx` 中 `PdfPage` | 画布完成后立即 `getTextContent()` 和 `TextLayer.render()` | 多页文本 DOM、字体布局与画布争抢主线程 |
| `pdf-render-scheduler.ts` | Set 顺序放行 continuation，没有可见优先级和耗时预算 | 屏外预取排在视口页前；一次 continuation 自身超过一帧预算 |
| `PdfPane.tsx` 可见性 effect | 离开 800 px 扩展范围释放画布/文本，再回来重建 | 往返滚动时重复解析、绘制与 GC |
| `PdfPane.tsx` 初始化 | 逐页取尺寸，全部结束后才设置可显示文档 | 长文首屏等待；页数多时初始化成本增加 |
| `PdfPane.tsx` pages/批注 | 全部页槽常驻；各页遍历全批注集合 | 长论文和大量批注时 DOM/遍历开销增长 |
| ResizeObserver 与 scale effect | 窗口或栏宽变化引发 scale 变化和绘制取消重启 | 拖中线、开侧栏时绘制频繁重启 |
| `App.tsx` 与任务状态 | 翻译进度、日志与计时在主应用层更新 | 需要 React Profiler 判断实际重渲染成本，不能仅凭存在更新定罪 |

PDF.js 的 `onContinue` 是协作式暂停点，`cancel` 也不保证打断任意正在执行的绘制。因此“每帧放行一次”并不等于“一次只用 4 ms”。[PDF.js RenderTask 文档](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-RenderTask.html)

## 3. 方案选择

| 方案 | 投入与风险 | 判断 |
| --- | --- | --- |
| 在现有渲染器补齐优先级、文本层调度和资源预算 | 中等，最大程度复用高亮/配对/同步能力 | 推荐主线 |
| 替换为 PDF.js 完整 viewer 组件 | 需要迁移双栏、批注、状态与样式；默认 viewer 也不是性能保证 | 仅在现有架构无法满足指标时小范围验证 |
| 更换原生 PDF 引擎或全部提前栅格化 | 包体、许可、跨进程坐标/文字层和维护成本高；预栅格化也耗时耗空间 | 当前不建议 |

## 4. 分阶段技术方案

### 阶段 A：复现与定位，约 1–2 人日

以当前实际安装版和对应源码构建作对照，确认用户运行的版本，避免修了源码但安装包未更新。记录 CPU、内存、GPU、屏幕刷新率、DPR、窗口大小和缩放。

选择问题论文与可公开分享的固定测试 PDF，录制持续下滑、急停、反向、两栏切换接管和拖动中线。采集 Chrome Performance/React Profiler/进程内存数据，并标注画布调度、文本层渲染、GC、IPC、字体加载及翻译后台活动。

交付前后 trace、可重复脚本、根因列表；没有证明的热点不贸然重构。Electron 官方也建议以实际 profiling 确定耗时部分，并避免主进程与渲染进程阻塞。[Electron 性能指南](https://www.electronjs.org/docs/latest/tutorial/performance)

### 阶段 B：交互优先调度，约 2–3 人日

统一管理两栏的“可见页、前向预取页、低优先级后台任务”，任务携带文档、页、缩放、generation、优先级和取消信号。

1. **优先级**：当前活动栏可见页 > 联动栏可见页 > 滚动方向前方少量页 > 其他预取；加入等待时长提升，避免某栏长期饥饿。
2. **generation**：切文档、缩放、改变渲染版本后丢弃旧任务和旧异步结果，避免取消后旧任务回写。
3. **预算**：60 Hz 下先以每帧约 4–6 ms 应用绘制工作为调参目标；通过 onContinue 控制启动/续绘，不能强行抢占 PDF.js 内部一段执行。若单段过长，需调整分辨率或评估可用的 worker rendering 能力，不宣称预算能保证硬上限。
4. **快速滚动**：保留已显示画面与页槽，不频繁清空；优先显示低成本预览，停止约 100–150 ms 后补清晰画布和非必要文本层。冷页预览与清晰层共享预算，不能同时大批启动。
5. **文本层**：与 canvas 分开排队；可见页尽快可选字，屏外层延后。正在拖选文字或有活动选区的页面固定保留，禁止为了性能销毁选区。
6. **输入**：保留浏览器原生滚动和 passive 监听；每帧最多提交一次联动目标，区分主动栏与程序同步，消除反馈环。不要给滚轮加几百毫秒防抖。

缩放和拖中线时先使用已有画布作视觉预览，在操作稳定后提交精确重绘；映射锚点由页码和页内位置维护，避免累计像素漂移。文字选区在缩放过程冻结或清楚提示暂不可选，缩放完成恢复准确文字层。

### 阶段 C：有上限的缓存与后台隔离，约 1–2 人日

- 对文本内容和邻近页预览做带容量上限的 LRU；保留少量刚离屏页，减少上下往返反复重建。键包含文档、页面、缩放/DPR 和渲染配置。
- 两栏合计设像素/估算字节预算，例如起步 128 MiB 栅格缓存，低内存档 64 MiB；这是缓存预算，不是整个进程 RSS 的保证。单页仍有像素上限。
- 活动选区与可见页不可被普通 LRU 淘汰；内存压力下先缩小预取，再降低预览分辨率。绘制结束/取消后再释放，避免破坏仍在用的 canvas。
- 用文档级共享观察器或可见范围计算取代每页独立 observer；是否进一步虚拟化页槽由 300/1,000 页的测量决定。虚拟化必须保留累计高度、跳页锚点和跨页选区，不能照搬固定高度列表。
- 批注预先按页索引，当前页只收到自己的批注数组；批注变化不应重算全部页面的标记。
- 首屏先读必要页尺寸，其他页后台补全；尺寸更正时固定阅读锚点。若实现复杂，可先缓存完整尺寸表，避免重复打开再次全扫。
- 翻译进度、日志、问答流式结果局部更新并限频，避免刷新整棵阅读组件；日志有长度上限，历史落盘异步。
- PDF 文本索引和重 CPU 处理放 worker/子进程；服务限流与渲染预算分别管理。引擎本来就在独立流程，仍需观察 CPU 竞争，不机械地再包一层 worker。

### 阶段 D：门禁和真实环境复验，约 1 人日

扩展现有 scroll smoke，保存分阶段原始采样，分别统计冷页加载和已加载页滚动，增加真实安装包运行。每轮至少 60 秒连续输入并重复 3 次；额外 10 分钟往返滚动检查资源是否持续增长。

## 5. 建议验收门槛

以下是拟定发布目标，不是本次已达到的结果。先在用户问题机器和参考机固定基线，再据硬件确认支持范围。60 Hz 设备暂定：

| 项目 | 发布目标 |
| --- | --- |
| 连续滚动帧间隔 | 每轮 P95 ≤20 ms、P99 ≤33.4 ms |
| 超 50 ms 帧 | ≤0.1%；支持测试集内无可归因于应用的 >100 ms 停顿 |
| 本地输入到反馈 | P95 <50 ms，不含网络等待 |
| 当前视口冷页 | 典型 PDF 预览 P95 ≤150 ms、清晰页 P95 ≤500 ms；重图/复杂矢量单列结果，不能藏进平均值 |
| 双栏联动 | 无来回抖动、无反向接管失败；稳定后目标位置误差不超过 2 px（布局对应成立时） |
| 内存 | 缓存不超配置预算；10 分钟重复循环后不持续单调增长，预热后末轮稳定占用较首轮不超过 10% |
| 正确性 | 无丢页、选区丢失、批注错位、旧任务覆盖新文档；缩放与跳页恢复正确 |

高刷新率设备按刷新周期制定单独门槛，不能用 60 Hz 的 20 ms 宣称 120 Hz 流畅。GPU/系统导致的异常帧也记录，剔除必须说明依据，不能随意删除坏数据。

测试矩阵至少包括：96 页现有夹具、300 页文本、扫描图像、复杂矢量/公式、混合页面尺寸、大量批注；单栏/双栏、DPR 1/1.5/2、50%/100%/300% 缩放；同时翻译、同时问答、窗口变化；鼠标滚轮及触控板。

## 6. 回退与最终交付

分别给调度策略、快速滚动预览、文本层延迟与缓存大小设置内部开关，逐项对照，出现空白或选区回归时能单项回退。先解决有 trace 证明的问题，再扩大虚拟化/引擎调整。

最终实现应交付：前后性能报告、问题 PDF 的回归脚本、安装版验证结果、支持范围及残余问题。**只有这些门槛通过，才能说指定范围的连续滚动卡顿已经解决；“一帧只画一个页面”本身不能作为验收结论。**
