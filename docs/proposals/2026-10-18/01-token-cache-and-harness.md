# Token 缓存、输出与 DeepSeek Harness 成本比较

日期：2026-10-18。结论：**当前最优选择是继续使用现有翻译网关直接调用模型，优化术语任务、思考输出和有效结果复用。暂不迁入官方 Harness。**这是基于现有架构和历史用量的工程判断，最终节省幅度须由同质量实验确认。

## 1. 95% 命中率是否能实现

必须分开三个指标：

| 指标 | 正确口径 | 能否以 95% 为目标 |
| --- | --- | --- |
| 服务端输入 token 命中率 | `sum(hit_tokens) / sum(hit_tokens + miss_tokens)`，仅统计返回完整有效 usage 的远端请求 | 热缓存、长公共上下文的特定负载可能达到；新论文批翻译不能保证 |
| 本地有效结果复用率 | 可直接复用的逻辑段落数 / 本次需处理的逻辑段落总数；完整 PDF 命中另计 | 对同文档、同策略、同上下文的重复任务可要求 ≥95%；完整 PDF 重开应零模型请求 |
| 有任意缓存命中的请求占比 | 命中 token 大于零的请求数 / 有有效 usage 的请求数 | 可能很高，但不能拿它冒充输入 token 命中率 |

服务端缓存只复用输入前缀，不会省去生成译文的输出。DeepSeek 官方说明缓存是尽力而为，并存在构建时间和淘汰机制，不能提供普遍的 95% 保证。[官方缓存规则](https://api-docs.deepseek.com/guides/kv_cache)

设每次请求有可复用前缀 P 和新内容 N，在前缀完全命中的理想热态下：

```text
命中率 H = P / (P + N)
H >= 95% 需要 P >= 19 × N
```

例如每批新增 1,000 token，就需要至少 19,000 token 可复用前缀。真实首批冷启动、术语变动和缓存淘汰还会降低整体命中率。因此，反复塞入全文或累积旧译文来凑 95%，可能让费用和延迟上升。若全文确实为消歧所需，可做独立实验，按总费用而非命中率决定是否采用。

**验收建议：把 95% 用于“相同任务重试的本地有效复用”，服务端命中率作为诊断指标。新论文首次翻译以质量、每万源文 token 费用、总耗时作为主指标。**

## 2. 当前实际情况

### 已经具备的能力

- `src/main/translation-prompts.ts`：固定规则前移，变化的术语与正文后移，已知 JSON 请求规范化。
- `src/main/translation-gateway.ts`：请求缓存、并发去重、保真省钱模式与 High 修复。
- `src/main/paragraph-cache.ts`：成功段落复用，缓存键保留原批次上下文与位置，不会随意跨语境复用。
- `src/main/cache-diagnostics.ts`：命中/未命中、思考 token、缺失字段及异常统计。
- `src/main/cache-scheduler.ts`：冷启动门控；当前由 `engine.ts` 中环境变量开关启用，并非默认开启。
- `src/main/cache-versions.ts`：翻译策略与排版版本已拆分。不能再把这些现成功能写作“从零新增”。

当前官方 DeepSeek 请求仍显式开启思考；已知模板在 economy 下使用 Low，异常项才 High 修复。因此“改成 Low”已经做过，下一步需研究哪些任务可以减少甚至取消思考，以及是否有必要重复提取术语。

| 类型 | 请求数 | 输入 token | 缓存命中 token | 输出 token（含思考） | 其中思考 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 正文批翻译 | 105 | 148,942 | 79,872 | 195,262 | 167,100 |
| 单段翻译 | 24 | 19,028 | 13,184 | 7,531 | 5,871 |
| 术语提取 | 54 | 64,012 | 41,344 | 298,178 | 272,181 |
| 其他 | 6 | 552 | 0 | 133 | 121 |
| 总计 | 189 | 232,534 | 134,400 | 501,104 | 445,273 |

输入缓存命中率 **57.80%**；思考占输出 **88.86%**；术语提取占输出 **59.50%**。扣除思考后的输出是 55,831 token，不应为了“输出低”压缩或漏译这些必要内容。

## 3. 费用计算：输出比追求 95% 更值得优先优化

按访问日官方英文价格页，`deepseek-flash` 每百万 token 峰时价格为：命中输入 $0.006、未命中输入 $0.30、输出 $1.20；谷时减半。这里只采用峰时统一示例，不做汇率换算。[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)

```text
模型费 = (命中输入 × 命中单价 + 未命中输入 × 未命中单价
        + 输出总量 × 输出单价) / 1,000,000
总运行费 = 模型费 + 工具/API 费 + 重试/复核费 + 基础设施费
```

思考 token 是输出的子集，不再加一次。未返回 usage 的中断请求单独标记未知费用，不能视为免费。

将上述历史 token 按当前峰时价格重新估算，得到以下敏感性分析；**这不是历史账单，也不是新优化实测**：

| 情景 | 估算模型费 | 相对基线变化 |
| --- | ---: | ---: |
| 历史 token 量，57.8% 命中 | $0.631571 | 基线 |
| 输入/输出总量不变，仅命中率升到 95% | $0.606138 | 约节省 4.03% |
| 输入不变、必要内容输出不变，仅思考量减半 | $0.364408 | 约节省 42.30% |

第三行是收益上限方向的示例，不代表已经能在相同质量下实现。真正该优先验证的是术语提取与思考模式，而不是只优化缓存百分比。

## 4. 与官方 DeepSeek Harness 的比较

Harness 是开源 agent 编排框架，当前官方仓库标注 developer preview，并提示兼容性变化；它不是一个换上地址即可享受更低模型单价的独立模型。[官方仓库](https://github.com/deepseek-ai/deepseek-harness)

其会话追加能保留可复用前缀，但旧消息会在后续步骤再次发送。翻译程序已有稳定前缀，迁入 Harness 本身不会自动消除思考 token，也不会免掉译文输出费用。[官方 Session 说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/session/README.md#model-experience)

| 选择 | 改造投入估算 | 持续调用与维护成本 | 适用性 |
| --- | ---: | --- | --- |
| A. 优化现有直接调用，推荐 | 4–7 人日 | 请求可控；复用现有缓存、取消与校验；维护面最小 | 当前固定流程的论文翻译 |
| B. 将每个翻译任务桥接给 Harness | 7–12 人日 | 同模型基础 token 单价仍按服务商计；增加桥接、进程、事件、升级与错误恢复工作 | 已有大量 agent 工具需要共用时 |
| C. Harness 长会话负责读文、规划、翻译、复核 | 10–18 人日 | 历史上下文、工具结果、规划和重试可能增费；也可能通过合理编排节省，需实测 | 开放式多资料研究，不是本次首选 |

估算包含适配、取消、结果结构、缓存隔离和回归，不是外包报价。B/C 若还要完成 A 的术语优化，不应假设 Harness 自带这些领域能力。尚未实作 B/C，因此不能声称测出了它们的精确单篇费用。

若开发日成本为 D，A/B 实际人日分别为 dA/dB，单篇费用为 cA/cB，则迁移回本所需篇数：

```text
N = ((dB - dA) × D + 新增维护费) / (cA - cB)
```

只有 `cB < cA` 才存在正向回本点。以本项目成熟的直接调用链路为基线，目前没有证据表明 Harness 可以提供这个单篇价差。因此 A 的总持有成本更有优势。

## 5. 推荐的具体改造

### P0：先验证收益，保留现有可用策略

1. 固定同一组论文、提取版本、模型实际返回版本，区分冷/热缓存；记录正文、术语、回退、语义复核各自费用。
2. 原始计数使用模型 usage；本地复用不记为服务端命中。增加“必要译文输出 / 思考输出 / 修复输出”可解释统计。
3. 保留 economy 作为基线，只做小规模非思考/Low 对照；不直接全局关闭思考。

### P1：术语先复用，再增量提取

- 建立文档术语表，保存术语、译法、原文定义出处、章节语境与版本；使用引擎提取结果构建，不另做一次全文重复请求。
- 相同已确认术语优先复用；新章节遇到多义词或定义冲突，只补充相关候选和局部上下文。
- 不把同一拼写跨学科、跨定义强行合并。新增术语表版本用于后续批次，不每次改写固定 system 前缀。
- 将术语提取规则与正文保真规则分开，保留术语所需的定义、歧义与 schema，减少无关全文规则。
- 原先 600→1,800 token 术语合批实验尚未通过完整联调，不能直接上线；仅在正确边界与上下文得到验证后比较批大小。

### P2：按任务与风险控制思考

- 候选策略：清晰定义和常规术语尝试非思考；普通正文保持 Low；复杂否定、条件、统计结论、公式关联及歧义段按风险送复核。
- 官方价格页确认存在非思考模式，但接入仍需按具体模型接口做参数兼容测试；未知兼容服务不注入专用参数。
- 数字、单位、占位符、ID、数量仍做确定性检查。语义高风险不能只靠现有数值检查发现，需额外抽检和风险路由。
- 只修复失败项，保留原批上下文；一次升级后仍失败就明确报告，避免无限复译。
- 输出预算依据批次内容设置足够余量；截断必须失败或拆批，不以压低上限换“省钱”。

### P3：提高有价值的缓存复用

- 延续固定前缀，移除其中时间戳/随机值；仅在有诊断证据时调整冷启动门控，不额外发送付费“预热”请求。
- 保持段落边界稳定，以减少重试时的缓存键漂移；不删除当前上下文敏感的缓存键字段来虚增命中。
- 保存带来源映射的结构化译文中间结果，使仅排版版本变化时可复用翻译。当前版本号拆分已存在，但仍需验证引擎能否直接回放译文完成重排。
- 不通过清空旧缓存使统计更好看；旧版结果保留，按兼容规则选择，批注保持版本隔离。

## 6. 实验与发布标准

建议至少 3 个学科、10 篇文本型论文，覆盖公式、双栏、长参考文献与复杂表格；抽取不少于 200 个段落，重点覆盖否定、限定条件和术语歧义。

- 同一源文分别对照当前 economy、新术语策略、候选非思考策略；每组分冷/热缓存并重复至少 3 次，随机化顺序，防止把热缓存当模型策略收益。
- 先离线回放测结构、取消和预算，再做有独立费用上限的真实实验；本次方案阶段不消费模型额度。
- 人工以原文为依据盲评，不能以 High 输出作为标准答案。新增严重语义错误为发布阻断；普通错误率不高于基线，并报告样本数及不确定性。
- 建议经济性目标：同质量下每万源文 token 总费用至少降低 20%，P95 总耗时不劣于基线 10%；这是立项目标，未达到则不宣称优化成功。
- 相同任务重试有效段落复用 ≥95%；同条件完整结果重开零远端调用。首次新论文不设不可控的服务端 95% 硬指标。
- 保留配置开关与旧策略回退，分别报告结构通过、语义检查和版面检查状态。

**最终选择：A。先把有限开发投入用在术语任务和不必要思考上；只有未来确实需要多工具、多资料研究，并且对照实验显示更低总成本时，再接 Harness。**
